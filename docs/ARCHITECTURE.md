# Restohub для Madi Cake: архитектура с админ-панелью

Документ состоит из двух частей:
1. Разбор MyTabMenu как референса: дизайн гостевого меню, функции, управление контентом.
2. Предлагаемая архитектура Restohub. Блюда, цены и наличие приходят из iikoCloud. Фото, тексты
   для гостей и оформление редактируются в нашей админ-панели.

Дата: 20.10.2026.

## 1. Референс: MyTabMenu

MyTabMenu (mytabmenu.com) — планшетное меню компании My Menu (mydigimenu.com). У них общая
админ-панель для планшетного меню, QR-меню, заказов и лояльности.

> **Как собраны данные.** Главная страница mytabmenu.com прочитана целиком. Сайт mydigimenu.com
> (справка и блог) из нашего окружения не открылся, сведения оттуда взяты через веб-поиск и
> помечены «(справка)». Всё это маркетинговые материалы. **Сам интерфейс меню и админки мы не
> видели**: скриншотов на сайте нет. Дизайн стоит оценить вживую — у них есть бесплатный пробный
> период без карты и 30-минутное демо.

## 2. Архитектура Restohub с админ-панелью

### 2.1. Принцип: кто чем владеет

| Данные | Источник | В админке |
|---|---|---|
| Состав меню: категории, блюда, порядок по умолчанию | Внешнее меню iikoWeb | Только просмотр; можно скрыть блюдо на планшетах и задать свой порядок |
| **Цены, размеры порций** | iiko | **Только просмотр.** Переопределить нельзя, расхождения видны в сверке цен |
| Вес, КБЖУ, аллергены | iiko | Только просмотр |
| Наличие (стоп-лист) | iiko `/api/1/stop_lists` | Только просмотр; на планшете «Закончилось» или блюдо скрыто |
| **Фото, галерея, видео** | Restohub (фото из iiko — запасной вариант) | Загрузка, кадрирование, порядок |
| **Название и описание для гостя** | По умолчанию из iiko | Можно переопределить (маркетинговый текст), есть перевод на en |
| Метки «Хит», «Новинка», «Сезон» | Restohub (+ теги iiko) | Да |
| «С этим берут» | Restohub | Выбор 1–3 блюд из меню |
| Обложки и описания категорий | Restohub | Да |
| Тема: цвета, шрифты, логотип, фон, раскладка | Restohub | Редактор темы с живым предпросмотром |
| Заставка и промо-баннеры | Restohub | Слайды, расписание показа |

Правило объединения простое: **поле из админки, если оно заполнено, иначе из iiko**. Цены,
размеры, КБЖУ и наличие в админке не редактируются вообще. Поэтому не возникнет ситуации, когда
на планшете одна цена, а на кассе другая.

### 2.2. Схема

```
                    ┌──────────────────────── iikoCloud ────────────────────────┐
                    │ внешнее меню · номенклатура · стоп-листы · фото (selstorage)│
                    └──────────────┬─────────────────────────────────────────────┘
                                   │ опрос раз в 5 мин (стоп-лист — раз в 1 мин)
┌──────────────────────────────────▼────────────────── сервер Restohub ───────────────┐
│  iiko/        клиент, синхронизация, сверка цен, стоп-лист → снимок iiko            │
│  content/     SQLite: фото, тексты, метки, пары, тема, заставка + история правок    │
│  media/       загрузка → сжатие → WebP/JPEG 400/800/1600 px → data/media            │
│  publish/     снимок iiko + контент + тема → опубликованная версия меню (JSON)      │
│  admin/       вход, роли, REST API админки, предпросмотр черновика                  │
│  tablets/     SSE-рассылка, реестр планшетов, приём аналитики                       │
└───────┬───────────────────────────────┬────────────────────────────────────────────┘
        │ /api/menu, /api/events (SSE)  │ /admin (вход по паролю)
┌───────▼─────────────┐        ┌────────▼───────────────────────────────┐
│ Планшеты (PWA)      │        │ Админка: компьютер или телефон менеджера │
│ кеш меню и фото     │        │ блюда · фото · тема · заставка · сверка  │
│ офлайн, киоск       │        │ цен · планшеты · аналитика               │
└─────────────────────┘        └────────────────────────────────────────┘
```

### 2.3. Черновик и публикация

Правки в админке сначала попадают в **черновик**, а планшеты показывают **опубликованную
версию**. Менеджер видит черновик в предпросмотре (гостевое меню в рамке админки с тем же
кодом) и нажимает «Опубликовать». Тогда сервер собирает новую версию и рассылает её планшетам.

- Данные из iiko (цены, стоп-лист, новые блюда) применяются **сразу**, без публикации: это
  факты, а не оформление.
- Каждая публикация сохраняется в истории, к ней можно откатиться одной кнопкой.
- Версия меню, которую получают планшеты, остаётся одним JSON с хешем, как сейчас.
  Гостевое приложение почти не меняется.

### 2.4. Что происходит при изменениях в iiko

| Событие в iiko | Поведение |
|---|---|
| Новое блюдо во внешнем меню | Сразу на планшетах с фото из iiko или заглушкой; в админке с пометкой «Нет своего фото» |
| Блюдо убрано из внешнего меню | Исчезает с планшетов; контент в админке сохраняется (пометка «Нет в iiko»), вернётся, если блюдо вернут |
| Цена изменилась в номенклатуре, но не во внешнем меню | Сверка цен показывает расхождение в админке (уже есть), по желанию — уведомление в Telegram |
| Блюдо в стоп-листе | На планшете «Закончилось» (или блюдо скрыто — настройка), обновление в течение минуты |

Контент привязан к `itemId` блюда в iiko (UUID). Он не меняется при переименовании или смене
цены.

### 2.5. Модель данных (SQLite, встроенный `node:sqlite`)

```
item_content    item_id PK, title, description, title_en, description_en,
                hidden, sort, badges[], pairings[], updated_at, updated_by
item_media      id, item_id, kind (photo|video), file, width, height, sort
category_content category_id PK, cover_media_id, description, columns, card_size, sort, hidden
theme           id, name, tokens JSON (цвета, шрифты, радиусы), logo_media_id, bg_media_id
screensaver     id, media_id, caption, link_item_id, starts_at, ends_at, sort
publication     id, version, created_at, created_by, snapshot JSON   ← история и откат
users           id, login, password_hash (scrypt), role (owner|manager)
devices         id, name, last_seen, app_version, current_version
events          ts, device_id, type (item_view|category_view|…), item_id   ← аналитика
```

Объём у одной кондитерской — сотни блюд и тысячи событий в день. Встроенного SQLite хватает с
запасом, отдельная база данных не нужна. Проверено: в Node 22 модуль `node:sqlite` доступен
(SQLite 3.50).

### 2.6. Фото

Опыт с Дорадо (фото слишком большого разрешения не загрузилось в iiko) — сильный аргумент
загружать фото для планшетов в Restohub, а не в iiko.

- Загрузка из админки: JPEG, PNG, HEIC с телефона, до 20 МБ.
- Сервер делает копии шириной 400, 800 и 1600 px в WebP и JPEG, убирает EXIF, учитывает
  поворот. Кадрирование 4:3 для карточки задаётся в админке.
- Планшет загружает подходящий размер через `srcset`. Для офлайна service worker заранее
  кеширует копии 800 px.
- Для сжатия нужна библиотека `sharp`. Это первая внешняя зависимость проекта, но она
  оправдана: без неё качественно сжимать фото не получится.

### 2.7. Тема и оформление

У гостевого меню уже есть дизайн-токены (CSS-переменные). Тема в админке — это редактор
значений этих токенов, а не свободная вёрстка. Поэтому тема не может сломать меню.

- **Цвета:** фон, бумага карточек, акцент, текст. Перед сохранением проверяется контраст.
- **Шрифты:** выбор из 6–8 подобранных пар (заголовок + текст). Шрифты хранятся на сервере, а
  не загружаются с Google Fonts, поэтому работают и офлайн.
- **Логотип, фон стартового экрана, скругления, число колонок, пропорции фото.**
- Живой предпросмотр: гостевое меню в рамке админки, тема передаётся без сохранения.

### 2.8. Админ-панель

Разделы:
1. **Меню** — дерево категорий и блюд из iiko. Иконки показывают статус: нет фото, нет
   описания, в стоп-листе, расхождение цены, нет в iiko. Карточка блюда: слева данные iiko
   (только чтение), справа редактируемый контент.
2. **Оформление** — тема, заставка, промо-баннеры.
3. **Публикация** — что изменено в черновике, кнопка «Опубликовать», история и откат.
4. **Состояние** — синхронизация с iiko, сверка цен (сейчас это `/status.html`), стоп-лист.
5. **Планшеты** — список устройств: онлайн или нет, версия меню, когда последний раз был на
   связи, кнопка «Перезагрузить». Новый планшет подключается как у MyTabMenu: открываем меню,
   сканируем QR из админки — планшет получает имя («Зал, стол 3») и попадает в список.
6. **Аналитика** (P3) — какие блюда открывают, по часам и дням.

Технически это отдельное одностраничное приложение `admin/`, которое сервер раздаёт по
`/admin`. Предлагаю Preact или React с Vite: там много форм, загрузка файлов и перетаскивание.
Гостевое меню остаётся на чистом JS без сборки, чтобы быстро работать на недорогих планшетах.

**Доступ:** вход по логину и паролю (scrypt из `node:crypto`), сессия в cookie с флагами
`HttpOnly` и `SameSite=Strict`. Роли: «владелец» (всё, включая пользователей) и «менеджер»
(контент и публикация). Если админка доступна из интернета, а не только из сети кондитерской,
нужен HTTPS и ограничение числа попыток входа.

### 2.9. Развёртывание

Один процесс Node на мини-ПК в кондитерской или на облачном сервере.

- **Мини-ПК в зале:** планшеты работают по локальной сети даже без интернета, фото раздаются
  быстро. Нужен ИБП и резервные копии.
- **Облачный сервер:** проще обслуживать и заходить в админку из любого места, но без интернета
  в зале планшеты живут только на своём кеше. Это уже предусмотрено.

Рекомендация для Madi Cake: **облачный сервер** (одна точка, офлайн-кеш на планшетах уже
есть), ежедневная резервная копия `data/` (SQLite + фото).

- Фото: проверка, поворот, без метаданных, копии 400/800/1600 px в WebP и JPEG (`sharp`).
- Админка `/admin`: вход, список с фильтрами, редактор блюда и категории, порядок, загрузка фото,
  предпросмотр в рамке планшета, публикация, отмена черновика, история и откат; работает на телефоне.
- Проверено на реальном iiko Madi Cake: правка → предпросмотр → публикация → гостевое меню.

Отличия от плана выше:
- Админка сделана на Preact + htm **без сборки** (без Vite): форм немного, а отказ от сборки упрощает
  развёртывание. Если админка разрастётся, перейти на Vite можно без изменений API.
- Кадрирование фото в админке отложено: на планшете фото заполняет карточку 4:3 по центру.
- HEIC не поддерживается сборкой `sharp` — загрузка возвращает понятную ошибку с подсказкой.
- Управление пользователями — пока из командной строки (`npm run admin:user`), роли сохраняются,
  но в P1 обе роли могут всё, кроме управления пользователями (его в интерфейсе нет).

### 2.10.2. Статус P1.1 (20.10.2026) — подготовка к пилоту

- **Синхронизация:** время последней успешной синхронизации переживает перезапуск; запасной снимок iiko;
  защита от сбойного ответа (меню с резко меньшим числом блюд удерживается до подтверждения владельцем);
  фото iiko сохраняются атомарно и только если это изображение; свежесть данных и предупреждения
  (`server/health.js`); стоп-лист: блюдо с одним размером, группы терминалов.
- **Офлайн:** детерминированный выбор размера фото, предзагрузка фото опубликованной версии в service
  worker с лимитом и очисткой прежних версий только после полной загрузки новой; копия меню в Cache API;
  таймаут сети для оболочки.
- **Безопасность:** права владельца и менеджера на сервере; CSRF (Origin, Sec-Fetch-Site,
  X-Requested-With); выход по простою; HTTPS — встроенный или за прокси; CSP и заголовки; управление
  пользователями; миграции схемы по `user_version`.
- **Обслуживание:** очистка неиспользуемых фото с сохранением истории публикаций; резервные копии с
  манифестом, проверкой и восстановлением; автокопии.
- **Админка:** полоса предупреждений, индикатор свежести данных, интерфейс по ролям, разделы владельца.
- **Проверка:** 48 автотестов, E2E в Chromium (`npm run e2e`), прогон на реальном iiko Madi Cake (только
  чтение). Установка и чек-лист пилота — [PILOT.md](PILOT.md).

Найдено при подготовке: на планшете по адресу `http://<IP>` браузер не включает service worker и Wake Lock,
то есть без HTTPS офлайн-режим и запрет гаснуть экрану не работают. HTTPS стал обязательным требованием.

### 2.11. Что меняется в текущем коде

- `server/sync.js` перестаёт сразу отдавать меню планшетам и сохраняет **снимок iiko**.
  Новый модуль `publish/` собирает из снимка, контента и темы опубликованную версию.
- `server/normalize.js` дополнительно сохраняет теги и данные стоп-листа. Формат меню для
  планшетов расширяется (`media[]` со `srcset`, `badges`, `pairings`, `soldOut`, `theme`),
  старые поля остаются.
- `public/app.js` берёт тему из меню, а не из CSS. Добавляются заставка, «Закончилось» и
  «С этим берут».
- `/status.html` переезжает в раздел «Состояние» админки.

### 2.12. Решения, которые нужны от клиента

1. Блюдо из стоп-листа скрывать или показывать с пометкой «Закончилось»?
2. Нужен ли английский язык на старте?
3. Где будет сервер: облако или мини-ПК в зале?
4. Кто будет вести контент и нужен ли доступ с телефона?
5. Нужны ли вызов официанта и заказы с планшета, или планшет остаётся витриной меню?
